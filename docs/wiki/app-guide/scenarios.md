# Scenarios

Re-sequence a concrete pour model and generate its programme (dev server only). You only need the model: load its IFC in **Inputs**, then open Scenarios.

1. **A project folder.** Scenarios works in a project folder — the same folder as the [project database](project-database.md#project-database). Pick yours in the Scenario panel, or use **Start without a project folder**, which works in `Documents\Insight Plan\Default project`. A folder laid out like the CWA planning tool's (`models`, `2-enriched-ifc`, `4-schedule-xlsx`) works as before.
2. **Add the model.** When the building loaded in Inputs is not in the folder yet, **Add to project** copies its IFC into `models`. The first time, preparing its pour list runs class fixing and clash detection (a few minutes); after that, updates take about a second. Adding a model again replaces it and clears what the app built from the old one.
3. **Model check.** Before and after adding, the **Model check** card says whether the generator can make a programme from the model: *Ready to generate*, *Will generate, with gaps* or *Cannot be generated* — see [What the generator needs from a model](#what-the-generator-needs-from-a-model). **Show** selects the elements concerned in 3D.
4. Scenarios are kept in the project database (`ip_scenario*` tables): each one's pour order, manual links and crews, per building. The generator's outputs (XML, caches) stay in `<project>/scenarios/<name>`. Scenario JSON files and Overrides workbooks from before the database are imported into it once, the first time it is opened.
5. **Order your search sets.** Open **Generate (classic)** (eight numbered tabs; Scenario opens first): the list is your search sets, top first, in the order they are built. Add one with **+ Add a work item…**, drag a row number to move it, and flip **per level** / **once**. Open a step (the chevron) to see the recipe it generates, its resources and its objects. See [Generate (classic)](#generate-classic). The objects one by one (the old SequenceOrder table) are on the **Sequence** tab.
6. **Update 4D** regenerates the programme for the order on screen and loads it straight into 4D, with no download or Inputs step. It uses a generator process that stays running and keeps the building's model and pour records loaded (`scenario-engine/serve.py`). After a warm-up when the scenario opens, an update takes about a second in the generator and about 3 s until 4D shows it. **Auto-update** does this a moment after each change. The first update for a building runs the whole generator once (`main.py`, XML only — no Excel) to build its geometry cache. **Save** keeps the order; XML / XER downloads stay available.
7. **Links** and **Crews** (side-pane tabs) edit the scenario's manual links (predecessor / successor activity IDs from the generated programme, with names and a warning for IDs it doesn't have; type; lag in hours) and its crew overrides (phase, optional pour type, trade, people; **Customise** copies a phase's default crews in to change them). They are saved with the order, and Update 4D uses them at once.
8. The same scenario works inside **4D Sequencing › Scenarios**, beside the 3D model: picking pours in the table selects them in 3D and the other way round, and double-clicking a pour moves the 4D timeline to the day its linked activity starts (Update 4D first, so the programme has that pour), and the Scenario panel is docked next to it. Both places share one state, so unsaved edits carry over.
9. **Steps.** In Models > Search sets, **Import steps…** reads a CSV / TXT (a column that identifies the objects — GlobalId or any model property, e.g. the Pour ID Number — and a task-name column, in construction order, e.g. a Navisworks TimeLiner export). Consecutive rows with the same task become a search set (that property is any of …) in the **Steps** folder, numbered 1, 2, …; rows without a task name are left out. In the scenario toolbar, **From steps** orders the pours by those sets — each step's pours start together — and pours in no step leave the sequence. You can then split steps and move pours as usual.
10. **Record picks.** In 4D > Scenarios, switch on **Record picks** and click pours in 3D one at a time; the count shows how many are remembered. **Sort by picks** puts them first, one step each, in the order picked; **Clear picks** forgets them.

## Generate (work packages)

**Generate** is the way to make a programme from a model: four steps in its header, with **Generate schedule** always in the bottom bar. It is on by default (Settings › Experimental features › Generate); the older eight-tab view below is **Generate (classic)**, shown only when Classic Generate is switched on there.

- **Getting started.** Until a plan is open, Generate shows one card for the next thing to do: load a model (or **Try the sample building**), choose where the plan is kept (**Use the default folder**, `Documents\Insight Plan\Default project`, or type your project folder), add the model to the project, then start or open a plan. **Try the sample building** loads a small three-storey model that ships with the app, groups it into work packages, generates its programme and saves the plan as *Sample plan*, so every step can be seen in a minute.
- **1 - Work packages**, **2 - Sequence**, **3 - Methods & Generate**: group the objects into packages (a package can hold others), put them in build order, check how each is built. **Advanced** holds the picked package's settings (days, crew, when it starts, extras).
- **4 - Granular sequence** (optional): the 4D view beside the object-by-object table. **Use this order in Generate** builds each package's objects in the table's order; **Follow it exactly** makes the table's steps the build order of the whole schedule, across the packages (the packages' own order and "starts after" links are then not used for the objects in the table; what it leaves out follows at the end). The chip beside them says what Generate does with the table now (click it to turn its highlight off or on). The tools are grouped (Order, History, Follow, Picks, Show); with **Record picks** on, a strip says so until you stop.
- **Versions.** The bottom bar's list switches plans; **Save as new version…** copies the plan on screen (packages, order, methods, days, crews, object order), saves and generates it, and switches to it. **Compare…** puts two versions side by side: length, critical share and the packages on the critical path, objects and volume, each with its change, and the packages whose method, days, objects, place, object order or criticality differ.

### The WBS

Step 3's **WBS…** (or Advanced › Set the WBS) sets how the programme's WBS is laid out.

- **Follow the work packages** (the default): a node for each package under the building's Construction node, nested as the packages are, in build order.
- **My own rules**: rules tried from the top for each activity; the first whose condition fits places it. A rule has a condition (a field, an operator such as *equals*, *contains*, *in*, *is empty*, and a value), where its path starts (under the building's **level** node, or under the **building**'s Construction node) and its **levels**, separated by `>`. A rule with no condition fits every activity: keep one last, as the fallback (an activity no rule fits goes straight under its level).
- A level is a name template: `{Field}` is the activity's value of a field, `{Field:title}` / `{Field:upper}` / `{Field:lower}` formats it, `{Field|text if set|text if not}` picks a text, `{parent}` is the node above. A level that reads an empty field is left out (write `{Field?}` for a field that may be empty). **Last level for phases** makes the last level for those phases only, e.g. `{parent} - {phase}` for a node per phase; **Every** makes a node for each of them, used or not.
- The fields are the packages' own: *Package*, *Package code*, *Package level 1*, *Package level 2*… (the packages it is in, outermost first), *Storey*, *IFC class* (when all its objects share one), *Method*, *Building*, *Object* (an object built on its own), and *phase*. Nothing is built in: the same rules work for any kind of project.
- The grid shows how many activities each rule places in this plan, and the **Preview** shows the tree with its objects and activities (roughly: the generator puts the building's code in the top names, and names the level nodes its own way).
- **Download Excel** gives the rules as a sheet (*WBS rules*: Order, On, Name, Starts under, Field / Operator / Value 1–3 (all must hold), Level 1–8, Last level for phases, Make every phase) with a *Read me*; **Upload Excel** replaces the rules with the sheet's rows, after saying how many it read and what it could not.
- The rules are saved with the plan. The generator's own WBS for pour models (classic scenarios) is a rule set too, `scenario-engine/wbs_default_rules.json`: the same format, nothing hard-coded in the generator.

## Generate (classic)

Work breakdown (tab 2) is the path (the tabs after it are optional): a planner who only knows search sets can order them and press **Generate** without opening any other tab.

- **1 - Scenario** (opens first): project folder, building, start date, Update 4D, Save, and the list of scenarios.
- **2 - Work breakdown**. Under the list, **Grouping levels**: define the work breakdown from the objects instead of from the list, like the Group panel. Each level is a property of the objects or a folder of your search sets, with a **role** (the **Work item** group a recipe is found by; Building, Level or Zone; or Structure only), a **sort** (by value, by the number in the value, as listed, or the order of the sets) and an on/off switch. The objects are grouped by the levels in order, and each group at the end is a work item, shown with its objects and quantity (the number of objects, or the sum of a numeric property you choose). An object with no value at the Work item level is left out; an object in several sets of a folder is in the first of them. When a level has the role Work item, **Update 4D** makes the programme from these work items, not from the list or the pours. Each activity carries its work item's id (the **Work Item** field), and a **Work items** Link Group is added for you, so 4D plays, colours and picks the item's objects; the list's 3D preview, the work-item rows' objects and the summary-bar counts read the same work items. A property can also be **Set › folder**: the name of the first set of that folder that holds the object. Then **Other build orders**: one table, a line for each work item of each other order that has to hold as well (an order may take its work items from a folder of search sets). Under the list, folded, **Levels and zones**: which property of the pour data is the level and the order the levels are built in, and which property is the zone and which of its values are **connected** to the rest of the building and which are **disconnected** (built on their own). Left alone, the generator reads the level from the first number in its text and a zone from the words Connected and Disconnected in the property Building Zone. Your search sets in build order on the left; on the right the 3D model with each step's objects in that step's colour (the same colour as the strip on its row number). Click a work item to colour only its objects (click it again, or **Show all steps**, to see every step); click an object in 3D to pick its work item, which opens in the list. Reordering or renaming a work item updates the colours at once. **Hide 3D** gives the list the full width; **Show 3D** brings it back. The colours are only a preview: nothing is saved with them and they come off when you leave the tab. **Generate** is always at the top right of the list.
- **3 - Sequence**: the model's objects one by one in the order they are built (the old SequenceOrder table, with its Columns / Filters / Group / Sort / Colour pane).
- **4 - Labour** (optional tab): one table, a line for each trade of each crew (a trade in several crews is simply repeated): Crew, Trade, Trade name, In crew (people of the trade in the crew), Number (people the site has of the trade), Gangs (how many crews there are), Productivity, Unit, Used for, Subcontractor. Productivity, Unit and Used for belong to the crew and are on its first line. It writes to the existing trades, crews, rates and recipe activities; nothing new is stored.
- **5 - Recipes**: how each group is built, only when the default chain of activities is wrong. The **Max at once** view of the grid sets how many of an activity may run together for that recipe's group.
- **6 - Parameters**: one table. A *value* is read by duration formulas; a *resource* is equipment, a crane or a material and how many there are, with its own Max at once. Under it, **Rates**: the named durations, productivities (man-hours per unit, with people, shifts and hours per shift) and rebar densities that recipe activities use. The productivity of a crew is also set on the Labour tab.
- **7 - Extras**: activities that are not built from the model, and (second tab) summary bars: one bar per building and level, from the first to the last object of a group, which other activities can be tied to (with **Level links**).
- **8 - Rules**, by what a rule is for: **Links between activities** (manual links and contact links), **Crews on a phase** (crew overrides) and **Generator settings**. A second tab, **All limits**, lists every limit; the single list of all rules, with its tools, is folded at the bottom.

Tabs 3 to 8 are optional: none is needed for a normal programme.

**Work breakdown.** The ordered list of search sets is the programme's work breakdown, so the workbook sheet that used to be called Steps is now **Work breakdown** (its columns are Item, Search set / group, Per level, Link into it, Lag, Notes). Workbooks made earlier, with a Steps sheet and a Step column, still upload. The list's rows are called work items.

## What the generator needs from a model

Only elements with the **CWA Pour** property set are pours; everything else in the model is ignored, and no other property set is needed. What CWA Codes holds (General Level 1–3, Full Pour ID) is worked out from CWA Pour, and CWA_Planning is the generator's own output. From CWA Pour it reads:

| Property | Needed for | When it is missing |
| --- | --- | --- |
| Pour Type | activity type code, durations, crews | **error** — the pour becomes "OTHER" |
| Pour Volume m3 | including the pour; rebar tonnes | **error** — counted as 0 m³ and left out |
| Pour ID Number | the pour number in the activity ID (four digits: 21 → 0021) | warning — the generator numbers the pour itself, after the building's highest number |
| Level | level code and WBS | warning — the pour goes on L0 |
| Building (and Unit) | building code in IDs and WBS | warning — "UNKNOWN" |
| Building Zone | zone code (C / D) | noted — no zone code |
| Is External? | EW / IW for walls | noted — walls taken as internal |
| Concrete Stage, Max / Min Elevation | stage 2, precast, double-height walls | optional |

Pours under **0.25 m³**, and the types **BOSS, SCREED, GROUT, SPECIAL**, are left out of the programme. Two pours with the same building, level, zone, type and pour number would get the same activity ID — the check flags them. The rules live in `scenario-engine/main.py` (reading the pours) and `config.py`; the app's check (`src/scenarios/modelCheck.ts`) follows them.
